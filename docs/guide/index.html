Guide

Getting started

jeli is a decorator-based framework: components, directives, services, and modules are declared with plain function calls immediately followed by a class or function declaration, then compiled by jeli-cli into a real, running application - no virtual DOM, no runtime template interpretation required if you opt in to compiled bindings.

Scaffold a new project

The CLI scaffolds a working project (component, module, jeli.json config) for you:

npm install -g @jeli/cli
jeli create my-app
cd my-app
jeli serve

Add jeli to an existing project

npm install @jeli/core @jeli/common
npm install --save-dev @jeli/compiler-cli @jeli/dev-cli

Every project needs a jeli.json describing its projects and build output - jeli create generates one for you; see CLI below for the shape if you're wiring one up by hand.

Core concepts

jeli's decorators - Element, Directive, Service, Provider, Pipe, jModule - look like TypeScript/TC39 decorators, but they aren't. Each is a plain function call whose argument object is discarded at runtime; jeli-cli recognizes the source-position adjacency of a call immediately followed by a class (or function) declaration and compiles the two together.

Why this matters The decorator call must sit directly above the class/function it annotates, with nothing in between. There's no @ prefix, and (with one narrow exception - Element, which collides with the DOM's own global Element interface in TypeScript) each decorator is typed as an ambient global function purely for editor autocomplete on the options object, not as a real class decorator. 
Service({ DI: [] })
export class LogService {
    log(msg) { console.log('[app]', msg); }
}

Your first component

An Element is jeli's component: a selector, a template, and a class or function constructor.

greeting.element.js
Element({
    selector: 'app-greeting',
    template: '<h1>Hello, ${name}!</h1>',
    props: ['name:string=World']
})
export class GreetingElement {
    // props declared above (name) are set on `this` before this
    // constructor's own body runs
}

Use it from another template like a native element: <app-greeting name="jeli"></app-greeting>.

OptionPurpose
selectorMust contain a hyphen - enforced at compile time (HTML custom-element naming rules).
template / templateUrlInline template string, or a path to an external .html file. Use a plain quoted string for inline templates, not a backtick template literal - jeli's compiler interprets ${ } inside the string itself; a real JS template literal would try to evaluate it first.
style / styleUrlComponent-scoped CSS, inline or external - automatically scoped to this component's own elements (Angular-emulated-style encapsulation, no Shadow DOM required).
propsBindable input properties: "name", "name:Type", or "name:Type=default".
eventsDOM event bindings declared at the decorator level (alternative to inline @event= template syntax): "click: onClick($event)".
DIDeclared dependencies - see Dependency injection.
viewChild / contentChild"field=#refId" per entry - queries a template-referenced (#refId) child element or component.
asNativeCompiles to a real customElements.define() Web Component instead of jeli's own renderer.

See the full option reference in the API docs.

Templates

Interpolation

Embed an expression in text content or an attribute with ${ }:

<p>${greeting}, you have ${todos.length} item(s).</p>
<p>${getSuccessRate().toFixed(1)}%</p>

Pipes transform a value inline with |:

<p>${user | json}</p>
<p>${createdAt | dateTime:'YYYY-MM-DD'}</p>

Property & attribute bindings

Wrap an attribute name in curly braces to bind it to an expression (evaluated whenever the component re-renders, not just once):

<div {class}="{'active': isActive, 'disabled': isDisabled}"></div>
<div {style}="{background: isDark ? '#000' : '#fff'}"></div>
<input {value}="currentValue">
<select {model}="selectedId">...</select>

A plain, unbound attribute (no { }) is passed straight through to the DOM as-is.

Event bindings

Prefix an event name with @. $event is available inside the expression:

<button @click="save()">Save</button>
<input @keyup="onKeyUp($event)">
<form @submit="addTodo()">...</form>

Two-way binding for form controls combines an event with a directive-value binding - see Forms for the full picture with @jeli/form.

Structural directives

jeli ships two equivalent ways to write conditional/repeated content: the original attribute-directive form, and (added more recently) an Angular-17-style block syntax. Both compile to the same output - pick whichever reads better to you.

Attribute-directive form

<div *if="isLoading">Loading…</div>
<div *if="user; else as noUser">Hi, ${user.name}</div>
<j-template #noUser><div>Please sign in.</div></j-template>

<li *for="todo of todos; idx=index">
    ${idx}: ${todo.description}
</li>

<div {:switch}="status">
    <p *switchCase="'loading'">Loading…</p>
    <p *switchCase="'error'">Something went wrong.</p>
    <p *switchDefault>Ready.</p>
</div>

Block syntax (@if / @for / @switch)

The same structural directives, written as top-level template blocks instead of attributes - no host element required:

@if (isLoading) {
    <div class="spinner"></div>
} @else if (error) {
    <p class="error">${error}</p>
} @else {
    <p>Hi, ${user.name}</p>
}

@for (todo of todos; idx = index) {
    <li>${idx}: ${todo.description}</li>
}

@switch (status) {
    @case ('loading') { <p>Loading…</p> }
    @case ('error') { <p>Something went wrong.</p> }
    @switchDefault { <p>Ready.</p> }
}

Blocks nest freely in any combination (@for inside @if, @switch inside @for, and so on) and are validated at compile time - an unclosed block, an empty condition, or a @case outside a @switch is a build error, not a silent runtime bug.

Template references & fragments

SyntaxPurpose
#refIdNames an element or component for later reference - from viewChild/contentChild, an *if; else as X fallback, or a @for/@switch's generated template.
<j-template #x>A named, not-rendered-by-default template fragment - rendered on demand (e.g. an *if's else branch).
<j-fragment>A dynamic template outlet - swaps its rendered content based on a runtime-selected template id.
<j-place>Content-projection slot, comparable to Angular's ng-content or Vue's <slot>.

Dependency injection

Declare what a component or service needs via the decorator's DI array; jeli resolves and constructor-injects it:

Service({ DI: [] })
export class CounterService {
    step(current, delta) { return current + delta; }
}

Element({
    selector: 'app-counter',
    templateUrl: './counter.element.html',
    DI: [CounterService]
})
export class CounterElement {
    constructor(counterService) {
        this.counterService = counterService;
    }
}

A DI entry can be:

  • A class reference (an imported Service/Provider-decorated class) - resolved as a singleton by default.
  • A plain string naming a registered service, e.g. 'MyService'.
  • 'name?' - trailing ? marks it optional (resolution failure yields null instead of throwing).
  • 'name=localAlias' - renames it for dynamicInjectors use.
Static runtime tokens need the trailing ? A handful of special values are injectable without being registered services - changeDetector, ElementRef, ViewRef, ParentRef, TemplateRef, HostElement, QueryList. Because the compiler can't statically distinguish these from a real (possibly missing) service name, request them with the optional marker even though they always resolve: DI: ['changeDetector?']. Requesting 'changeDetector' without it fails to compile with service not found: changeDetector. 
Element({
    selector: 'app-panel',
    templateUrl: './panel.element.html',
    DI: ['changeDetector?']
})
export class PanelElement {
    constructor(changeDetector) {
        this.changeDetector = changeDetector;
    }
}

ProviderToken

For DI values that aren't classes (config objects, primitives), use a ProviderToken and register it on a module:

import { ProviderToken } from '@jeli/core';

export const API_BASE_URL = new ProviderToken('ApiBaseUrl');

jModule({
    services: [
        { name: API_BASE_URL, useValue: 'https://api.example.com' }
    ],
    ...
})
export class AppModule {}

Lifecycle hooks

Define any of these as instance methods - jeli calls them automatically at the matching point in a component's life:

HookFires
didInit()After DI resolves and the constructor runs, before the first render.
viewDidLoad()After the view is first rendered and inserted into the DOM (also when viewChild/contentChild queries are populated).
viewDidDestroy()Right before the component is torn down - clear intervals/subscriptions here.
 
Element({ selector: 'app-clock', template: '<span>${time}</span>' })
export class ClockElement {
    constructor() { this.time = new Date().toLocaleTimeString(); }
    didInit() {
        this._tick = setInterval(() => { this.time = new Date().toLocaleTimeString(); }, 1000);
    }
    viewDidDestroy() { clearInterval(this._tick); }
}

Change detection

By default, jeli re-checks every binding in every mounted component, root to leaf, on any trigger - a DOM event, an HTTP response, a router navigation. There's no fine-grained dependency tracking; it's a full sweep, every time. This keeps state sharing between unrelated components working with zero explicit wiring, at the cost of scaling less gracefully in very large trees.

Opting a component out of the sweep

A component whose state is genuinely local to itself (nobody else reads it) can detach from the automatic cascade and trigger its own re-render explicitly:

Element({
    selector: 'app-dashboard',
    templateUrl: './dashboard.element.html',
    DI: [MetricsService, 'changeDetector?']
})
export class DashboardElement {
    constructor(metricsService, changeDetector) {
        this.metricsService = metricsService;
        this.changeDetector = changeDetector;
    }
    didInit() {
        this.changeDetector.markAsManual();
        this.poll();
    }
    poll() {
        this.metricsService.getMetrics().subscribe((data) => {
            this.metrics = data;
            // re-render just this component - the automatic
            // cascade no longer reaches it after markAsManual()
            this.changeDetector.manualCheck();
        });
    }
}

rxWatch(source, changeDetector, onNext) is a small helper for the common case of "subscribe to a long-lived Subject, and re-render (via manualCheck()) on every emission":

import { rxWatch } from '@jeli/core';

didInit() {
    this.changeDetector.markAsManual();
    rxWatch(this.sharedStateService.updates, this.changeDetector, (value) => {
        this.value = value;
    });
}
This is opt-in, not the default Reach for markAsManual/rxWatch when you've confirmed a specific component is a real performance bottleneck - most components should keep the default behavior, the same tradeoff Angular's OnPush makes.

Modules & bootstrapping

jModule groups services, components/directives, and declares an app's root component:

import { CommonModule } from '@jeli/common';
import { AppRootElement } from './app.component';
import { CounterElement } from './counter.element';

jModule({
    requiredModules: [CommonModule],
    selectors: [AppRootElement, CounterElement],
    services: [CounterService],
    rootElement: AppRootElement
})
export function AppModule() {}
import { bootStrapApplication } from '@jeli/core';
import { AppModule } from './app/app.module';

bootStrapApplication(AppModule);

Compiled bindings

By default, template expressions are interpreted at runtime against a small AST. Opt in to compile them to real JS functions ahead of time via jeli.json:

{
  "projects": {
    "my-app": {
      "output": { "..." : "..." },
      "buildOptions": {
        "compiledBindings": true
      }
    }
  }
}

This trades a slightly bigger build step for faster expression evaluation at runtime - no behavior change, purely a performance option.

Walkthrough: build a Todo app

Scaffold a project and replace the generated root element with the following.

todo.element.js
Element({
    selector: 'app-todo',
    templateUrl: './todo.element.html',
    styleUrl: './todo.element.scss'
})
export class TodoElement {
    constructor() {
        this.pageHeading = 'My First Todo App';
        this.todos = [];
        this.description = '';
    }

    addTodo() {
        if (!this.description) return;
        this.todos.push({ description: this.description, done: false });
        this.description = '';
    }

    removeTodo(index) {
        this.todos.splice(index, 1);
    }

    toggleDone(index) {
        this.todos[index].done = !this.todos[index].done;
    }

    get remaining() {
        return this.todos.filter((t) => !t.done).length;
    }
}
todo.element.html
<h1>${pageHeading}</h1>

<form @submit="addTodo()">
    <input {value}="description" @input="description = $event.target.value" placeholder="What needs doing?">
    <button type="submit">Add</button>
</form>

<p>${remaining} of ${todos.length} remaining</p>

@if (!todos.length) {
    <p>No todos yet.</p>
} @else {
    <ul>
        @for (todo of todos; idx = index) {
            <li {class}="{done: todo.done}">
                <input type="checkbox" {checked}="todo.done" @click="toggleDone(idx)">
                <span>${todo.description}</span>
                <button @click="removeTodo(idx)">Remove</button>
            </li>
        }
    </ul>
}

This exercises: interpolation, a getter used as a computed value, a submit-triggered event binding, an @if/@else block, a @for block with an index, and a class binding driven by state - the same core mechanics every real jeli app builds on.

Forms

@jeli/form adds reactive form controls: FormControlService (a named group, like Angular's FormGroup) holding FormFieldControlService instances (a single field, like Angular's FormControl), plus a set of value accessors (checkbox, radio, select, number, range) so {:model}-style two-way binding works correctly across native input types. See the Form API reference for the full surface, including the formControl/formField/fieldControl directives and validators.

HTTP

@jeli/http's HttpService returns a Subject per request (not a Promise/Observable) that you .subscribe(onSuccess, onError) to. Both an XHR transport (default) and an opt-in fetch()-based transport are available; interceptors register against the HTTP_INTERCEPTORS token.

import { HttpService } from '@jeli/http';

Service({ DI: [HttpService] })
export class UsersService {
    constructor(http) { this.http = http; }
    getUsers() { return this.http.get('/api/users'); }
}

Full surface, including the fetch-transport opt-in and CSRF cookie handling, in the HTTP API reference.

Router

@jeli/router's RouterModule.setRoutes([{name, url, component, ...}]) registers route definitions (name, URL, component, named outlets, lazy-loaded children) and drives navigation via either the History API or hash-based routing. See the Router API reference for the full route-definition shape, guards, and the location-service internals.

TypeScript

Every package ships hand-authored .d.ts types (@jeli/core, @jeli/common, @jeli/form, @jeli/http, @jeli/router) covering both the runtime API and each decorator's option-object shape (ElementOptions, DirectiveOptions, ServiceOptions, ProviderOptions, PipeOptions, JModuleOptions).

jeli-cli does not compile .ts source The compiler only understands .js/.jeli files - types are for editor tooling (autocomplete, // @ts-check on plain .js) rather than a TypeScript build pipeline. One exception: Element itself isn't declared as a global function (it collides with the DOM's own built-in Element interface) - type the options object directly instead: const opts: ElementOptions = {...}; Element(opts);
